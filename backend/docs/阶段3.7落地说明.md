## 2. 迁移脚本设计

### 2.1 入口

```bash
cd backend
python -m app.scripts.migrate_sqlite_to_pg
# 或
python -m app.scripts.migrate_sqlite_to_pg \
    --source sqlite+aiosqlite:///./data/novelforge.db \
    --target postgresql+asyncpg://novelforge:novelforge@127.0.0.1:5432/novelforge
# 干跑
python -m app.scripts.migrate_sqlite_to_pg --dry-run
```

### 2.2 执行步骤

1. **读 SQLite 全表** —— sqlite3 同步驱动, 顺序读 28 张表
2. **校验目标 schema** —— 28 张表都应已存在 (Alembic upgrade head 已跑), 否则报错退出
3. **逐表迁移** —— `INSERT ... ON CONFLICT DO NOTHING` 走 PG 原生 SQL, 不依赖 ORM, 简单可靠
4. **行数对比** —— 4 张关键表 (projects / study_materials / chapters / agent_tasks) 行数 100% 一致

### 2.3 表迁移顺序

按 FK 依赖从父到子, 28 张表分 4 批:

```
1. 顶层父表 (无依赖)
   projects, model_providers, agent_roles, worker_status,
   prompt_templates, llm_cache_entries, behavior_cards, audit_logs

2. 依赖 projects
   bibles, outlines, chapters, worker_policies, agent_tasks,
   agent_steps, agent_events, memory_*, study_materials,
   project_study_material_links, agent_model_bindings,
   discussion_sessions, review_settings, chief_agent_sessions

3. 依赖 chapters / study_materials
   chapter_versions, review_comments, study_*,
   deepstudy_*, evolution_nodes

4. 依赖 agent_tasks / study_chapters
   template_usages, genre_prompt_mappings, prompt_auto_fill_batches,
   behavior_card_uses, model_*, prompt_versions, discussion_*,
   chief_agent_*
```

### 2.4 JSON 列处理

- SQLite 读出来是字符串 (`"{...}"`)
- 脚本预解析 → dict
- INSERT 时再 `json.dumps` → PG JSONB
- 验证脚本 (verify_migration.py) 反向抽样校验 JSONB 可解析

### 2.5 大表分批

`_BATCH_SIZE = 1000` 行/批, 走 `executemany` 风格 (`text(...).execute(...)` 多值).

## 6. 风险与回滚

| 风险 | 缓解 | 回滚 |
|------|------|------|
| 目标库有残留数据 | 脚本不 DROP, 只 INSERT; ``ON CONFLICT DO NOTHING`` 保证幂等 | 跑前 `DROP DATABASE novelforge` 重建 |
| 某张表迁移失败 (FK / 列类型) | 失败时抛错, 事务回滚, 源库不动 | 修脚本再跑 |
| JSON 解析失败 | _coerce_json_columns 走 try/except, 失败保留字符串 | PG 接受文本, 不会 500 |
| 时间列字符串格式 | naive UTC, PG 接受 | 用 `created_at::timestamptz` 强转 |
| 迁移脚本本身有 bug | 迁移是脚本不是 ORM, 简单可读, 加单元测试 | 改完重跑即可 |
