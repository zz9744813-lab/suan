## 2. 执行模型

```
POST /api/projects/{id}/launch (mode=semi_auto|full_auto)
   ↓
launch_semi_auto / launch_full_auto
   ↓ 创建 AgentTask (status=pending)
routers/projects.py
   ↓ enqueue
   ├─ project_bootstrap  → q:writing
   │     ↓ handler 跑完 project_bootstrap
   │     ↓ find_first_chapter_id(project_id)
   │     ↓ enqueue_chapter_task(first_id)
   │
   └─ chapter_pipeline (chapter_id)
         ↓ handler 跑完 chapter_pipeline
         ↓ enqueue_next_chapter(project_id, chapter_id)
         ↓ find_next queued chapter by chapter_no
         ↓ enqueue_chapter_task(next_id)
         ↓ ... 循环至无 queued chapter
```

---

## 3. 关键设计

### 3.1 chapter_id 复用为 task_id

业务约定: ``AgentTask.task_id`` (写入 arq) 在 chapter_pipeline 模式下 = `Chapter.id`. 这样
``run_agent_task(task_id=X)`` 通过 X 即可拿到 Chapter 行 (worker._run_chapter_pipeline 内部 db.get AgentTask 然后读 chapter_id).

### 3.2 chain 推进在 `finally` 后

```python
finally:
    await _mark_terminal(task_id, ok=ok, error=err)
    if ok:
        # chapter_pipeline → enqueue_next_chapter
        # project_bootstrap → enqueue first chapter
```

为什么放 finally: 不让链式入队的失败影响当前 task 的终态写入.
任务完成, 状态已写库, 链入失败只 log warning.

### 3.3 兼容

``worker_run_in_process=True`` 时, 路由走老 httpx 自调 /api/worker/start 路径, 不入队.
这阶段保留这个开关, 让本地 SQLite 回归不被卡.

### 3.4 失败重试语义

| 阶段 | arq 重试 | 用户体验 |
|---|---|---|
| chapter_pipeline 失败 | 任务回 running → 重新跑 | 该章最终要么 succeeded 要么 failed (DLQ) |
| chain enqueue 失败 | 不重试, 仅 log warning | 当前章已 succeeded, 下一章不会被自动入队; 客户端可以手动触发 |
| bootstrap 失败 | 任务回 running → 重新跑 | 整书卡在 bootstrap; 用户重启/重试 |

业务想要“bootstrap 失败也能让首章继续” — 那就把链入拆成单独 worker 任务, 3.6 之后再考虑.

## 5. 风险与回滚

| 风险 | 缓解 | 回滚 |
|------|------|------|
| chain enqueue 失败, 整书卡住 | 客户端可手动调 `/api/worker/start`; 或重启 backend-worker 让 in-process 兜底 | 关 backend-worker, 改 .env `WORKER_RUN_IN_PROCESS=true` |
| chapter_pipeline 与 chapter_id 业务约定被改 | chapter_pipeline handler 内 db.get AgentTask 仍读 chapter_id, 字段名不动 | 无需回滚 |
| bootstrap 失败时不会链入首章 | 业务需确保 bootstrap 跑成功; 失败场景下手动重启 backend-api 触发 | 手动修 |
