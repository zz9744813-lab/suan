## 二、加速改造：校准健身房（本轮主体）

### 设计（对应评审结论"五个杠杆"）

1. **Open-Meteo 数据源**（`app/core/weather/provider.py`）：免费无 key（github.com/open-meteo/open-meteo）。
   `trust_env=False` 绕本机代理陷阱；climatology = 2015-2024 十年同期 ±7 天基线，一次拉取进程内缓存；
   实况近 7 天走 forecast past_days，更早走 archive（ERA5 有 ~5 天滞后的兜底分派）。
2. **阴性对照域**（`app/services/weather_gym.py`）：每天恰好 2 个预注册事件——
   降水 ≥0.1mm（Null=十年同期频率，出界 [0.15,0.85] 即弃选）+ 最高温 ≥ 气候 50 分位（Null≈0.5）。
   判定零人工裁量，evidence 带实测值；术式在该域"跑赢 Null"优先怀疑泄漏（C-006）。
3. **provenance 溯源标**（predictions.provenance，轻量迁移 ALTER TABLE）：
   `live` / `backfill` 严格分账——回填只作校准种子与引擎体检，永不混入 live 技能统计。
4. **机械验证**：`POST /api/weather/verify-due` + scheduler 08:05 job；复用 `_record_request`/`_score`，
   不跑个人学习闭环（防污染规则库）。天气域**排除出人工验证收件箱**（防主观先判覆盖客观实测）。
5. **回填**：`POST /api/weather/backfill?start=&end=&stride_days=`，走与 live 完全同构的冻结链
   （同候选、同阈值、同哈希），refuse 未来区间、同区间幂等去重。

### Scheduler（launcher 打包版默认 SCHEDULER_ENABLED=true，开发机仍由 .env 控制）

| 时刻 | job | 内容 |

| 08:05 | weather_verify | 昨日天气机械验证 |

## 三、修复细节与理由

### 死锁修法（沿用 round 24 "保留首次+追记" 哲学）

- 入口：`existing_outcome.needs_confirmation=False` 才 409（C-003 只锁已归档行）。
- 补确认：原 OutcomeRecord **原地更新**（outcome_id 不变，无双行），旧判定进 evidence 前缀
  `[补确认留痕]`，request 留痕由 `_record_request` 追记。
- 已计分行第三次改口仍 409（测试覆盖）。

### Origin 守卫（app/api/deps.py）

`Sec-Fetch-Site: cross-site` → 403；带 Origin 且 host 非本地 → 403；无头客户端（curl/调度器/TestClient）放行。
挂在 verify / generate / export / weather POST。

### 前端 hooks 拆分

`FortuneSection` 只做守卫，主体平移进 `FortuneSectionBody`（props 传 data+chart，正文零重排），
`selDy` useState 变为无条件执行；`isCurrent` 本有 null 守卫，fallbackAge 改为 undefined 语义安全。
