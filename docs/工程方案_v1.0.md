# 玄鉴 XuanMirror
## 个人智能未来预测、验证与自校准系统工程方案

> 版本：v1.0  
> 定位：传统术数计算 + LLM 多智能体推演 + 现实数据 + 主动预测 + 结果验证 + 统计校准 + 对抗性审查  
> 核心原则：**Prediction → Freeze → Reality → Verify → Score → Diagnose → Learn → Predict Again**

---

# 0. 项目定义

## 0.1 这不是一个“AI 算命聊天机器人”

传统产品的工作方式通常是：

```text
用户提问
  ↓
排盘/起卦
  ↓
LLM 生成解释
  ↓
结束
```

玄鉴的目标不是“解释得像大师”，而是建立一个真正可以长期运行、主动生成预测、接受现实检验并持续校准的系统：

```text
系统主动寻找可预测事件
  ↓
多术式独立计算
  ↓
生成候选预测
  ↓
对抗性审查
  ↓
预测预注册并冻结
  ↓
提前展示给用户
  ↓
等待现实发生
  ↓
主动要求用户验证
  ↓
结果结构化
  ↓
计算预测误差
  ↓
判断每个术式、规则、Agent 的贡献
  ↓
调整权重 / 标记错误规则
  ↓
进入下一轮预测
```

系统的真正产品不是“命盘”。

系统的真正产品是：

> **一个不断被现实检验的个人 Future Model。**

# 1. 第一性原理

## 1.1 最终问题

如果目标是“预测未来”，那么最基本的问题只有六个：

1. 系统在结果发生前预测了什么？
2. 预测发生的概率是多少？
3. 事件什么时候应该发生？
4. 什么现实证据算“发生”？
5. 什么现实证据算“没有发生”？
6. 预测失败后，系统有没有真正受到惩罚并修正？

如果无法回答以上问题，那么无论输出多专业，都不能称为预测系统。

---

## 1.2 系统最高宪法

### C-001 可证伪原则

无法失败的预测，不允许进入正式预测账本。

禁止：

```text
最近可能有些变化。
需要注意人际关系。
未来存在机遇。
可能先坏后好。
```

允许：

```text
预测窗口：2026-09-01 ~ 2026-09-07

事件：
至少发生一次未在前一日计划中的工作任务，
并造成原计划改变 ≥ 30 分钟。

预测概率：
0.67

验证：
发生 / 未发生 / 部分发生 / 无法判断
```

---

### C-002 预测先于结果原则

正式预测必须在结果发生前：

- 生成；
- 写入数据库；
- 写入完整时间戳；
- 保存模型版本；
- 保存 Prompt 版本；
- 保存术数规则版本；
- 保存输入快照；
- 计算内容哈希；
- 冻结。

结果出现以后禁止覆盖原预测。

---

### C-003 不允许事后改口

预测发布后如果需要修订，只能：

```text
Prediction v1
↓
Revision v2
```

而不能覆盖 v1。

原版本永久存在。

---

### C-004 全失败样本保留

不能只保存“算准了”的预测。

系统必须永久保存：

- 命中；
- 未命中；
- 部分命中；
- 无法验证；
- 用户拒绝验证；
- 数据不足；
- 被对抗审查拦截。

---

### C-005 概率而不是绝对断言

核心输出必须使用概率。

例如：

```text
工作临时变动：68%
计划外消费：61%
收到非日常联系人消息：43%
重大岗位变化：12%
```

而不是：

```text
今天必有贵人。
```

---

### C-006 不得假设传统术数具有科学预测效力

紫微、八字、六爻、奇门、梅花、面相、掌纹等作为：

> Traditional Metaphysical Signals

进入系统。

其有效性必须由系统自己的长期验证结果决定。

---

### C-007 现实优先

涉及真实世界决策时：

```text
现实证据 > 可验证历史规律 > 传统术数解释
```

尤其是：

- 医疗；
- 法律；
- 财务；
- 安全；
- 高风险职业决策。

系统不得以术数预测代替专业判断。

# 4. Prediction Budget：禁止“撒网式算准”

## 4.1 为什么必须有预算

如果系统每天预测：

```text
100 件事
```

最终发生 20 件，再只展示 20 件：

> 命中 20 项。

这是无效实验。

---

## 4.2 强制下注制度

默认：

| 类型 | 每周期最大正式预测数 |
|---|---:|
| 明日强预测 | 5 |
| 明日观察预测 | 5 |
| 7 天预测 | 5 |
| 30 天预测 | 5 |
| 90 天预测 | 3 |

只有最高信息价值的预测才能获得预测额度。

---

## 4.3 Information Value

候选预测评分：

```text
IV =
Novelty
× Confidence
× Falsifiability
× Personal Relevance
× Model Disagreement Value
```

优先发布：

- 系统非常有把握；
- 多模型明显分歧；
- 与用户现实高度相关；
- 可清楚验证；
- 对模型校准价值高。

# 11. Null Model

整个项目必须有一个：

> 完全不知道任何术数的预测模型。

Null Model 只允许使用：

- 历史事件频率；
- 星期；
- 工作日；
- 已知日程；
- 用户计划；
- 近期行为；
- 时间序列；
- 简单统计。

例如：

```text
问题：
明天是否出现计划外工作？

历史基础概率：52%
Reality Model：58%
传统融合：69%
```

只有传统模型长期稳定超过 Null Model，才能说明：

> Traditional Signals 提供了额外信息。

# 17. Outcome Verification

验证时系统主动提醒。

例如：

```text
P-20260830-001

昨天预测：
会出现一次临时工作安排，并改变原计划 ≥30分钟。

实际发生了吗？

A. 发生
B. 未发生
C. 部分发生
D. 无法判断
E. 直接描述今天发生了什么
```

用户可以直接自然语言回复：

```text
下午突然让我去处理一个事情，
本来准备做别的，耽误两个小时。
```

OutcomeJudge 输出：

```json
{
  "prediction_id": "P-20260830-001",
  "outcome": 1.0,
  "confidence": 0.94,
  "evidence": "临时任务造成约2小时计划改变",
  "needs_confirmation": false
}
```

# 18. 部分命中

不要强迫所有事情二值化。

支持：

```text
0     = 未发生
0.25  = 极弱部分发生
0.50  = 部分发生
0.75  = 高度发生
1     = 完全发生
```

但：

> 每一种预测的 grading rule 必须在预测冻结前确定。

不能事后调整评分规则。

# 19. 评分系统

## 19.1 Brier Score

```text
BS = (p - y)²
```

例：

```text
预测 80%
实际发生

(0.8 - 1)² = 0.04
```

---

## 19.2 Log Loss

用于严厉惩罚极端错误概率。

---

## 19.3 Calibration

例如历史预测：

```text
所有标 70% 的预测
实际发生率应该接近 70%
```

显示：

```text
Predicted     Actual
10%           13%
30%           28%
50%           47%
70%           61%
90%           76%
```

如果 90% 实际只发生 76%：

> 模型明显过度自信。

---

## 19.4 Sharpness

一个模型如果永远预测：

```text
50%
```

虽然可能校准不错，但毫无信息价值。

因此同时统计：

> Sharpness

鼓励模型真正做出区分。

---

## 19.5 Skill Score

与 Null Model 比较：

```text
SkillScore =
1 - ModelLoss / NullLoss
```

如果：

```text
> 0
```

说明超过 Null Model。

如果：

```text
<= 0
```

说明所谓高级模型还不如基础概率。

# 20. 对抗性审查系统

这是核心基础设施，不是附属 Agent。

## 20.1 VaguenessAttack

攻击：

> 预测是否模糊到怎么解释都成立？

例如：

```text
明天可能有变化。
```

直接 Reject。

---

## 20.2 BarnumAttack

判断是否属于：

> 大多数人、大多数日子都成立。

例如：

```text
你今天可能有些情绪波动。
```

Reject / 降权。

---

## 20.3 DefinitionAttack

攻击定义。

例如：

```text
会遇到贵人。
```

系统必须问：

```text
贵人是什么？
怎样记录？
怎样判断没有遇到？
```

无法定义则 Reject。

---

## 20.4 TimeWindowAttack

```text
未来可能……
```

Reject。

必须具有明确时间窗口。

---

## 20.5 CherryPickAttack

检查：

- 是否遗漏失败预测；
- 首页是否只展示成功；
- 报告是否隐藏低表现模块。

---

## 20.6 MultipleTestingAttack

统计：

```text
候选预测数
正式发布数
命中数
```

如果 Agent 每天产生大量预测：

> 候选命中不得算作正式命中。

只有冻结的 Prediction Ledger 才计分。

---

## 20.7 RetrofittingAttack

检查结果产生以后：

- event description 是否修改；
- criteria 是否修改；
- probability 是否修改；
- time window 是否修改。

---

## 20.8 OutcomeLeakAttack

检查预测生成时是否已经包含结果信息。

尤其：

- 日记已经记录；
- 日历已经确定；
- 用户已经明确告诉系统；
- 网络数据已经显示结果。

有泄漏：

```text
LEAKED
```

不进入预测评分。

---

## 20.9 SelfFulfillingAttack

例如系统预测：

> 你今天会主动学习。

用户看到以后因为预测才去学习。

这是：

```text
Potential Self-Fulfilling Prediction
```

需要单独标记。

---

## 20.10 BaselineAttack

询问：

> 不使用术数，只用历史概率，会不会一样预测？

必须和 Null Model 比。

---

## 20.11 AgentCollusionAttack

检查不同 Agent：

- 输出文本相似度；
- 结论同步异常；
- 是否偷偷获得其他 Agent 输出；
- 是否由同一 Prompt 模板造成伪独立。

---

## 20.12 CorrelatedEvidenceAttack

紫微、八字、黄历等可能共享同类历法信号。

不能因为：

```text
4 个术式支持
```

就错误理解成：

```text
4 个独立证据
```

建立：

```text
Evidence Dependency Graph
```

降低相关证据重复计权。

---

## 20.13 ConfirmationBiasAttack

检查 Outcome Judge 是否倾向把模糊现实描述判成“命中”。

应同时运行：

```text
Prosecution Judge
Defense Judge
Neutral Judge
```

出现分歧则：

```text
NEEDS_USER_CONFIRMATION
```

---

## 20.14 NarrativeExcuseAttack

禁止失败以后输出：

```text
只是应期延后。
能量已经发生。
可能以另一种形式应验。
这是潜在影响。
```

除非：

> 延迟窗口规则在预测冻结之前已经注册。

否则一律判失败。

# 76. 不允许的实现捷径

## 禁止 1

```text

然后让它自己同时算紫微、八字、六爻、奇门。
```

必须 deterministic engine。

---

## 禁止 2

```text
把所有专家报告一起交给 LLM，
然后让它“综合判断”。
```

必须先结构化 Signal。

---

## 禁止 3

```text
让 LLM 自己判断自己有没有预测准。
```

必须 Outcome Schema + Rule + 对抗 Judge。

---

## 禁止 4

```text
用命中率一个指标。
```

必须概率评分。

---

## 禁止 5

```text
失败以后重新解释直到“应验”。
```

被冻结定义优先。

---

## 禁止 6

```text
一开始人为规定紫微 30%、八字 25%……
```

初始只允许弱先验。

长期由实证数据学习。

# 86. 项目最终硬性原则

> **未经验证的预测不是知识。**

> **无法失败的预测不是预测。**

> **发生以后才补出来的解释，不算预测能力。**

> **如果 Null Model 比玄学模型更强，就必须承认玄学模型没有贡献。**

> **所有命中与失败必须同时保留。**

> **LLM 负责解释、假设、归因与综合；确定性计算必须交给程序。**

> **任何“系统变得更准”的结论，都必须由冻结预测和后验现实数据证明。**

> **第一性原理审查和对抗性检测不是一次性设计步骤，而是系统自身永久运行的组成部分。**
