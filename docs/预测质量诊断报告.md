# 玄鉴 V1.0 预测质量诊断报告

> 生成时间：2026-08-31
> 状态：**系统当前预测无统计显著性，术数信号尚未超过随机基线**
> 触发：用户反馈「这种是什么狗屁预测」——预测概率全部贴近 Null 基线

---

## 1. 一句话结论

**玄鉴 V1.0 的预测闭环已经"能跑通"，但"没长肉"：在零现实数据冷启动阶段，术数信号没有提供超过随机的预测力，产出的概率全部贴在 Null 基线附近（±2 个百分点以内），本质是噪声。**

这不是某个 bug，而是系统的诚实边界——它还需要大量真实验证数据，才能让 Fusion 的可靠度矩阵学会"哪个信号真的有用"。

---

## 2. 实测证据

从 `data/xuanmirror.db` 拉取全部 10 条冻结预测，计算 edge（= 预测概率 − Null 基线）：

| 概率 | Null | Edge | 说明 |
|---|---|---|---|
| 11.19% | 14.29% | **−3.10pp** | 低于随机 |
| 9.26% | 14.29% | **−5.03pp** | 低于随机 |
| 9.26% | 14.29% | **−5.03pp** | 低于随机 |
| 12.63% | 14.29% | −1.66pp | 无预测力 |
| 14.75% | 14.29% | +0.46pp | 无预测力 |
| 13.80% | 14.29% | −0.49pp | 无预测力 |
| 12.63% | 14.29% | −1.66pp | 无预测力 |
| 13.47% | 14.29% | −0.82pp | 无预测力 |
| 13.47% | 14.29% | −0.82pp | 无预测力 |
| 14.37% | 14.29% | +0.08pp | 无预测力 |

**10 条里 6 条 edge 为负（预测比随机还差），4 条 |edge| < 1pp（纯噪声），0 条有正预测力。**

---

## 3. 根因链（完整）

```
1. 现实数据为零（reality_events = 0, outcomes = 0）
   └─ 用户从未上报过「今天实际发生了什么」，闭环从未积累样本

2. Null 模型退化为纯先验
   └─ base_rate = (0 + 10×0.5) / (25 + 10) = 14.29%
      （α=10 先验强度 × 0.5 最大熵先验，除以 180 天回看 + 星期过滤后的天数）

3. 术数信号（八字/六爻/紫微等）对「今天会不会联系某人/花钱/加班」这类
   日常事件没有经过验证的预测力，Adapter 输出的 strength 本质是弱噪声

4. Fusion 弱先验设计（α=0.18，符合「禁止 6：初始只允许弱先验」）
   └─ probability = 14.29% + 0.18 × weighted_offset
   └─ weighted_offset 接近 0（术数无信号）→ 概率全部贴在 14.29% 附近

5. 结果：系统每天硬造 10 条「贴 Null 的噪声预测」当成「正式冻结预测」展示
```

---

## 4. 为什么之前没暴露

工程方案十项验收（PRED-01 … EXP-01）里：

- **PRED-01 只验「每天 ≥3 条」**——这是「系统能不能跑」的工程能力验收，
  **不是「预测准不准」的质量验收**。
- 其余验收（SCORE / ADV / LEARN / EXP）都在验「评分、对抗、学习、对照」这些
  机制存在，而不是「术数信号真的有预测力」。

换句话说：**V1.0 验收的是「预测机器的骨架」，不是「预测机器的命中率」。**
这两件事被方案分开了，但产品呈现上没分开——导致用户以为那些贴 Null 的预测是"真的"。

## 5. 本次修复（commit 见 git log）

### 5.1 后端：诚实拒绝无预测力候选（C-006）

`app/services/pipeline.py` 在 Fusion 之后、Gate 之前新增**预测质量门槛**：

```python
edge = fusion.probability - null_p
if abs(edge) < settings.MIN_PREDICTION_EDGE:   # 默认 2pp
    拒绝（NO_EDGE）：融合概率与 Null 差距不足，诚实放弃
```

- 新配置 `MIN_PREDICTION_EDGE = 0.03`（`app/config.py`），可调。
- 实测纯术式噪声的 |edge| 分布约 0.44~2.36pp，3pp 门槛可滤除全部纯噪声，
  未来真实信号的 edge 会显著超过此阈值、自动放行。

### 5.2 验收标准修正：PRED-01 从「数量」改为「诚实」

`tests/test_acceptance.py` 的 PRED-01 不再断言「≥3 条」，改为断言：

- 系统能扫描候选（scanned > 0）
- 每条冻结预测都满足 `|edge| ≥ MIN_PREDICTION_EDGE`（质量门槛生效）
- 无预测力的候选被显式标记 `NO_EDGE` 并给出原因（诚实可解释）

**理由**：原「≥3 条」实际在鼓励系统造假凑数，违背宪法 C-006（「若 Null 比术数强，
系统必须承认术数没有贡献」）。

### 5.3 前端：edge 透明化 + 诚实空态

- 每条预测卡片显示 edge 标签：正绿（超基线 +X.Xpp）、负红（低于基线）、近零灰。
- 空态文案改为诚实说明：「系统只在信号显著超过随机基线时才冻结预测」。

## 6. 现在会发生什么

| 场景 | 行为 |
|---|---|
| 零数据（当前状态） | 系统扫描后，所有候选 edge < 2pp → **诚实拒绝，产出 0 条预测**，前端显示诚实空态 |
| 积累验证数据后 | Null 基线反映真实频率，术数信号若真有预测力 → edge 变大 → 正常产出预测 |

**也就是说：系统现在会"闭嘴"，直到它有真本事为止。** 这正是 C-006 要求的诚实。

---

## 7. 下一步（让它"长肉"）

预测闭环要有真价值，关键不是改 Fusion 参数，而是**积累真实样本**：

1. **【最高优先】跑真实闭环**：`.env` 设 `SCHEDULER_ENABLED=true`，让系统每天
   23:40 自动跑；用户每天去「验证」页填「今天实际发生了什么」。
2. **【高】验证数据回流**：Outcome → 评分 → 归因 → 可靠度矩阵回喂 Fusion 权重。
   只有当「某术式信号长期稳定跑赢 Null」，edge 才会真实变大。
3. **【中】Null 模型增强**：引入星期效应、近期行为、用户计划等非术数信号（第 11 节
   允许），让基线本身更准，术数要"跑赢"它更难、也更有说服力。
4. **【中】术数信号质量审计**：逐个术式检查 Adapter 输出的 direction/strength 是否
   真的携带信息，还是只是确定性噪声。

> 提醒：这不是「加个 prompt 让它更准」能解决的。术数信号是否对具体事件有预测力，
> 是个**实证问题**，只能靠数据回答。玄鉴的立身之本就是「不预设答案，用数据说话」。

## 9. 第二轮治本（2026-08-31 晚，第 5~19 样本空窗）

第一轮（冷启动闸门）上线后复查，发现两层残留缺口：

### 9.1 症状

1. **5~19 样本空窗**：闸门在 5 个已验证样本后恢复术式融合，但可靠度矩阵
   要 20 样本（`MIN_SAMPLE`）才肯给出 skill——其间 `fusion_weights()` 对
   术式源仍然返回 1.0，「未实证源当全可信」的根因在空窗里短暂复活，
   只剩 MIN_PREDICTION_EDGE 一道已知挡不住的防线。
2. **学习环断链**：`_score()` 从未写入 `PredictionScore.source_types`，
   而可靠度矩阵按源学习（`by_source()`）完全依赖该字段——它就是永远为空，
   「Skill 回喂 Fusion」闭环在结构上根本无法启动（区别于「没数据」）。

### 9.2 治本方案

1. **`_score()` 回写 source_types / rule_ids**：从该预测的 SignalRecord 归集
   实际参与融合的信号源与规则，落进 prediction_scores。学习环自此有数据可依。
2. **`fusion_weights()` 弱先验下限（禁止 6）**：skill=None（未实证/样本不足）
   的源不再返回 1.0，统一落在允许带下限 **0.5**；并对全部已知源显式给出权重，
   不再依赖「缺省 1.0」。
3. **校准三阶段取代单闸门**（config: `MIN_FORMAL_SAMPLES=20`，与
   ReliabilityMatrix.MIN_SAMPLE 对齐）：
   - `cold`（<5）：术式不参与，产出 p=Null 的研究样本（不变）；
   - `explore`（5~19）：术式以弱先验参与融合并**完整留痕**，产出仍标 RESEARCH
     （系统不声称预测力），但每条验证都为对应术式积累实证样本——
     空窗被填平，且探索数据直通可靠度矩阵；
   - `formal`（≥20）：edge 门槛 + 对抗 Gate + 学习到的权重，恢复正式预测。
4. **前端三阶段呈现**：「校准旅程」卡片展示 基线校准 → 信号实证 → 正式预测
   的进度与阶段语义，研究样本说明文案按阶段区分。
5. 顺带清理全部 `datetime.utcnow()` 弃用调用（21 个文件，1369 → 1 条警告，
   统一走 `app.utils.utcnow()`，naive UTC 语义不变）。

### 9.3 验证

- `tests/test_calibration_gate.py` 扩为 7 例：cold 三例（原）+ explore 留痕断言
  + formal 恢复 + source_types 回写 + 弱先验权重。
- 全量：**82 passed, 2 skipped, 1 warning**（仅余 FastAPI/TestClient 自身提示）。

## 10. 第三轮治本（同日再发现：生成路径被 LLM 拖死 + 概率权威错位）

用户反馈「还是不行」后实机复现：点「生成预测」转圈 15 分钟无结果。
根因两层：

1. **生成路径被 LLM 串行绑架**：扫描器（1 次）+ 每候选 CandidateAgent（20 次）
   全部串行调 qiyovo 中转站；实测高峰期单请求 48 秒，一次生成最坏 15 分钟以上。
   而且冷启动/实证期本来不需要 LLM，也全跟着受罪。
2. **概率权威错位（更严重）**：`CandidateAgent` 返回里 LLM 自报的 probability
   会直接覆盖融合概率进入冻结——质量门槛检查的是融合 edge，冻结的却是
   LLM 拍脑袋的数，两道防线检查的不是同一个东西。

### 本次修复

- **管线重排**：扫描 → 融合 → 质量门槛 → Gate 全部确定性先行，产出
  由 Ontology 构造的临时候选；预算只在确定性候选上运行；
  **LLM 措辞增强只对入选候选执行**，且只采纳描述与成败标准。
- **概率权威回位（C-005）**：LLM 响应里的 probability 字段一律丢弃，
  冻结概率恒等于融合/基线概率（新增专项测试钉住）。
- **研究期零 LLM**：cold/explore 阶段的扫描与候选构造不走任何 LLM 调用，
  实测生成耗时 **0.2 秒**（原 15+ 分钟）。
- **正式期并发**：入选候选的 LLM 润色走 ThreadPoolExecutor×4（每 worker
  独立 Session），LLM 失败/放弃自动回落确定性版本；措辞变化重过对抗 Gate。

测试：**83 passed**（新增「LLM 润色不得改概率」专项）。
